# 1. Introduction 简介

## 1.1. Purpose 目的

本文档详细描述曲靖国家级零碳园区能碳管理平台“数据管理”模块的产品定位、页面结构、主要交互、输入输出、数据来源、状态、校验、跨模块联动及一期边界。本文档作为产品、前端、后端、测试和项目业务人员的统一沟通依据，用于指导原型实现、接口和数据结构设计、测试用例编制及后续版本验收。

本版需求以“不过度设计、先保证数据管理主链路可落地”为原则：对企业唯一标识、能源节点与流向关系、正式事实数据、数据状态、来源追溯、问题下钻等研发必须遵守的规则进行明确；完整规则引擎、复杂数据血缘、复杂能源转换与多来源分摊等能力不在本期展开。

## 1.2. Scope 范围

本文件覆盖数据管理模块四个子页面：数据总览、企业档案、能源与设施、业务数据。模块面向园区管委会及园区运营管理人员，以园区数据底座维护和业务支撑准备度判断为核心。

- 数据总览：汇总企业纳管、数据覆盖、正式入库、数据问题及IOC/零碳指标支撑状态。

- 企业档案：维护园区企业主数据、园区归属、空间位置、稳定基础属性及企业标签。

- 能源与设施：维护能源来源、能源节点、能源设施及长期有效的能源流向关系。

- 业务数据：统一查询、维护和追溯能源、运营、碳排放、零碳专项等期间型事实数据。

本期不包含：后台版IOC、复杂数据中台、通用数据血缘平台、完整外部接口采集平台、复杂能源网络仿真、复杂数据问题审批流，以及专业组织碳核算、产品碳足迹等服务全过程。

# 2. General Description 总体概述

## 2.1. About the Product 产品介绍

曲靖国家级零碳园区能碳管理平台用于支撑园区零碳建设、日常运营、IOC展示、零碳指标管控及后续验收。数据管理模块是平台数据底座，不以展示园区能耗或碳排放结果为核心，而以“统一对象、统一事实、统一来源、可追溯、可下钻”为核心。

平台当前以人工维护、企业填报、园区存量资料及专业服务结果回流为主要数据来源；外部系统或接口接入作为后续扩展能力。所有业务应用应优先消费数据管理中的正式数据，不为IOC、指标或验收另行维护一套重复事实数据。

## 2.2. 数据管理模块定位

| **页面**   | **核心问题**           | **主要职责**                                                 | **不负责**                                          |
|------------|------------------------|--------------------------------------------------------------|-----------------------------------------------------|
| 数据总览   | 这些数据整体可不可用？ | 聚合数据准备度、问题和业务支撑风险，并提供下钻处理入口。     | 不展示综合能耗、碳排总量、结构趋势、TOP5等IOC结果。 |
| 企业档案   | 企业是谁？             | 维护企业身份、园区归属、空间位置、稳定属性、标签和纳管状态。 | 不保存月度能源量、碳排量、数据完整率等期间事实。    |
| 能源与设施 | 能源网络是什么？       | 维护能源来源、设施/节点和长期流向关系。                      | 不维护月度消费趋势、流线宽度、TOP5等IOC展示结果。   |
| 业务数据   | 实际发生了什么？       | 统一维护期间型正式事实数据、状态、来源和追溯。               | 不计算零碳指标达标结论，不承担完整填报/问题工作流。 |

## 2.3. 页面与业务关系

四个页面不是平行的数据展示页，而形成“基础对象→网络关系→业务事实→数据治理与业务支撑”的数据链路。

| **链路**      | **处理路径**                                                                         | **说明**                                                         |
|---------------|--------------------------------------------------------------------------------------|------------------------------------------------------------------|
| 企业纳管      | 企业档案 → 纳管企业 → 业务数据/填报任务/IOC引用                                      | 企业通过enterpriseId作为稳定关联键，不按企业名称建立跨模块关系。 |
| 能源网络      | 企业档案 → 能源节点/设施 → 流向关系 → 业务能源数据 → IOC能源流向态势                 | 节点和长期关系由能源与设施维护，期间能源量来自业务数据。         |
| 数据补齐      | 数据总览 → 待处理数据事项 → 判断责任 → 填报任务/对应维护页 → 正式业务数据 → 总览恢复 | 数据总览发现问题，不重复建设数据录入表单。                       |
| IOC与指标支撑 | 正式业务数据/主数据 → IOC与指标计算 → 数据总览反向判断支撑状态                       | 业务结果由正式数据聚合计算，不反向写为另一套业务事实。           |

## 2.4. 核心数据与实现原则

1\. Enterprise为企业主数据唯一对象；enterpriseId创建后保持稳定，企业更名不得导致历史数据断链。

2\. 园区/园中园使用稳定ID作为企业、能源节点和业务数据的空间归属引用；页面显示名称不作为跨模块关联键。

3\. EnergyNode只保存能源节点/设施的稳定属性；EnergyFlowRelation保存长期有效关系；月度流量优先由正式能源数据关联或聚合，不在能源与设施页面形成第二套人工流量库。

4\. BusinessDataRecord作为业务事实统一框架；相同对象、数据项、期间不得存在两条同时有效的正式记录，正式修订必须保留版本。

5\. dataStatus描述业务生命周期，qualityStatus描述数据质量，两类状态不得混用。

6\. DataItemDefinition定义“这是什么数据”；DataRequirementRule定义“谁在什么场景下应该有它”；本期不建设通用规则配置后台。

7\. DataIssue作为隐藏数据治理对象，可由数据总览或业务数据打开同一问题详情；不新增“数据问题”左侧菜单。

8\. 正式数据必须保留来源类型和必要的sourceRecordId/凭证，以支持任务、接口、园区维护或专业服务结果追溯。

9\. 绿电属于电力属性，不与电力并列作为独立能源类型；相关来源可进一步标识直连、中长期交易、绿证对应等。

10\. 无数据不得静默补0；0仅在业务真实值明确为0时使用。

# 3. Functional Requirements 功能需求

## 3.1. 数据管理

数据管理模块包含数据总览、企业档案、能源与设施、业务数据四个子页面。各页面通过稳定ID、统一数据状态与来源追溯规则形成同一数据底座，为三张IOC、零碳指标管控、填报任务及验收提供数据支撑。

### 3.1.1. 数据总览

#### 3.1.1.1. Introduce 介绍

数据总览用于汇总园区当前数据底座的覆盖、正式入库、待处理事项及业务支撑状态，帮助管委会快速判断当前数据是否足以支撑三张IOC、零碳指标计算和后续验收。页面本质为数据治理入口和数据准备度判断页，不展示综合能耗、碳排总量、能源结构、企业TOP5等业务结果。

页面自身不维护第二套业务数据。数据问题需根据类型下钻至企业档案、能源与设施、业务数据或填报任务处理；处理完成后由系统重新计算总览状态。

#### 3.1.1.2. UI Design UI设计

页面顶部设置年度、截至月份、园中园和企业范围筛选。第一层展示纳管企业、数据项覆盖率、正式入库率、待处理事项、业务支撑风险5项摘要；第二层展示数据域准备情况；第三层展示IOC支撑状态和零碳指标数据准备状态；底部展示企业数据覆盖情况及高优先级待处理数据事项。页面以数值卡、状态标签、进度条和表格为主要表达方式，不使用大型趋势图、饼图或园区地图。

#### 3.1.1.3. 查询条件与数据准备摘要

#### 3.1.1.3.1. Inputs 输入

| **输入项** | **类型**   | **是否必填** | **范围**          | **备注**                                         |
|------------|------------|--------------|-------------------|--------------------------------------------------|
| 年度       | 年份选择器 | 是           | 当前及历史年度    | 默认当前年度；用于确定当年数据要求和统计范围。   |
| 截至月份   | 月份选择器 | 是           | 1-12月            | 当前年度默认当前已发生月份；历史年度可默认12月。 |
| 园中园     | 下拉框     | 否           | 全部/指定园中园   | 来源于园中园基础配置。                           |
| 企业范围   | 下拉框     | 否           | 全部企业/重点企业 | 默认全部企业。                                   |
| 查询       | 按钮       | —            | —                 | 应用当前筛选并刷新全页。                         |
| 重置       | 按钮       | —            | —                 | 恢复默认筛选。                                   |

#### 3.1.1.3.2. Process 处理

1\. 进入“数据管理 \> 数据总览”，系统加载默认年度、截至月份、全部园中园和全部企业范围。

2\. 用户调整筛选后点击“查询”，系统确定当前统计范围内的企业、数据要求和业务支撑对象。

3\. 系统统计已纳管企业数、当前应纳管企业数、应有数据项、已取得数据项、正式数据项及未关闭待处理事项。

4\. 系统根据IOC和零碳指标的数据依赖关系汇总当前受影响的IOC页面数量和指标数量。

5\. 五项摘要、数据域准备、业务支撑、企业覆盖和待处理事项必须使用同一组已生效筛选条件。

#### 3.1.1.3.3. Output 输出

- 纳管企业：已纳管企业数 / 当前应纳管企业数。

- 数据项覆盖率：已取得的应有数据项 ÷ 当前范围内应有数据项。

- 正式入库率：当前正式可用数据项 ÷ 已取得数据项。

- 待处理事项：缺失、异常、待确认、来源冲突、超期未更新、关系不完整等未关闭数据事项数量。

- 业务支撑风险：受影响IOC数量 / 3，以及受影响零碳指标数量 / 当前适用指标总数。

#### 3.1.1.3.4. Usage Limitation 约束与限制

- “应纳管企业”以企业档案中当前统计范围内的待纳管+已纳管企业为基础，已退出企业不进入当前应纳管分母。

- 数据项覆盖率不得直接使用“已有数据库记录数÷总记录数”，必须依据数据项适用要求判断。

- 正式入库率不把草稿、待审核、已退回、已作废记录计入正式数据。

- 业务支撑风险不采用黑箱综合评分，只展示实际受影响IOC和指标。

- 无数据时展示“—/暂无数据”，不得按0参与覆盖率或业务判断。

- 本功能版本边界：一期核心/P0；研发范围为筛选、聚合、状态判断和下钻。

#### 3.1.1.4. 数据域准备情况

#### 3.1.1.4.1. Inputs 输入

| **输入项**       | **类型** | **是否必填** | **范围**                                                                                              | **备注**                                             |
|------------------|----------|--------------|-------------------------------------------------------------------------------------------------------|------------------------------------------------------|
| 当前页面筛选条件 | 系统参数 | 是           | 年度/截至月份/园中园/企业范围                                                                         | 承接3.1.1.3已生效条件。                              |
| 数据域定义       | 系统配置 | 是           | 企业档案、能源设施、能源消费、绿色电力、能源流向、碳排放、运营数据、零碳专项、碳资产/绿证、降碳成果等 | 本期可按项目已有数据域固定配置，不建设通用配置后台。 |

#### 3.1.1.4.2. Process 处理

1\. 系统按当前筛选条件读取数据域定义及其适用对象范围。

2\. 企业档案按“已完成必填主数据企业数÷应纳管企业数”判断覆盖；能源消费按“已取得应报能源数据项÷应报能源数据项”判断；能源流向按“已配置有效关系÷应配置关系”判断；零碳专项按“本年度适用专项数据已完成÷应完成”判断。

3\. 系统分别统计覆盖率、正式入库率、待确认数量、异常数量、最近正式更新时间及业务影响范围。

4\. 根据关键缺口及业务影响生成正常/风险/缺失（或严重风险）状态。

5\. 用户点击某一数据域时，系统根据域类型下钻至企业档案、能源与设施或业务数据，并携带当前筛选和问题条件。

#### 3.1.1.4.3. Output 输出

- 列表字段：数据域、覆盖对象、数据覆盖率、正式入库率、待确认、异常、最近更新、影响范围、状态。

- 默认优先展示存在业务支撑风险或关键数据缺口的数据域。

#### 3.1.1.4.4. Usage Limitation 约束与限制

- 不同数据域允许使用不同覆盖规则，但前端统一显示“数据覆盖率”。

- 能源设施不得按“设施记录数量越多越完整”判断，应根据应配置节点/关系要求判断。

- 绿色电力的数据准备度应结合绿色电力量、来源/属性和必要凭证，不得把绿电当作独立能源品种。

- 数据总览只读取聚合结果，不提供直接修改业务数据字段的入口。

#### 3.1.1.5. IOC与零碳指标支撑状态

#### 3.1.1.5.1. Inputs 输入

| **输入项**       | **类型** | **是否必填** | **范围**                       | **备注**                                       |
|------------------|----------|--------------|--------------------------------|------------------------------------------------|
| 当前页面筛选条件 | 系统参数 | 是           | 当前年度及范围                 | 与全页保持一致。                               |
| IOC数据依赖      | 系统配置 | 是           | 3张IOC及其关键数据项           | 用于判断数据是否足够支撑展示。                 |
| 指标数据依赖     | 系统配置 | 是           | 当前适用零碳指标及其基础数据项 | 用于判断“数据是否准备好”，不用于展示指标结果。 |

#### 3.1.1.5.2. Process 处理

1\. 系统读取零碳园区总览、能源流向态势、碳排放与降碳态势三张IOC的关键数据依赖。

2\. 对每张IOC统计关键数据项完成情况，并识别缺失、待确认或异常数据是否影响当前展示。

3\. 系统读取当前适用零碳指标的基础数据依赖，判断分子、分母及必要支撑数据是否已准备。

4\. IOC显示正常/存在风险/无法支撑（必要时）；零碳指标显示正常/风险/缺失。

5\. 点击“查看数据缺口”定位待处理事项或业务数据；点击“查看指标”跳转零碳指标管控页面。

#### 3.1.1.5.3. Output 输出

- IOC支撑：页面名称、状态、关键数据项完成数、主要问题、查看缺口。

- 零碳指标准备：指标名称、数据准备状态、主要问题、查看问题/查看指标。

#### 3.1.1.5.4. Usage Limitation 约束与限制

- 本区域不得展示清洁能源消费占比、单位能耗碳排放等指标的实际结果值；实际结果由零碳指标管控页面负责。

- IOC趋势、结构、TOP5、热力等展示结果不作为数据管理中的独立事实表维护。

- 数据依赖关系可先采用项目固定映射，不要求一期建设通用可视化规则配置器。

### 3.1.2. 企业档案

#### 3.1.2.1. Introduce 介绍

企业档案是园区企业主数据的唯一管理入口，用于回答“园区有哪些企业、企业是谁、属于哪个园中园、位于哪里、具备什么稳定基础属性和零碳相关标签”。页面不承担能耗、碳排、指标或服务分析。

系统统一使用Enterprise作为企业主对象。enterpriseId为内部永久唯一标识；统一社会信用代码执行现实业务唯一性校验；企业名称仅用于展示，企业更名不得改变enterpriseId或切断历史数据引用。

#### 3.1.2.2. UI Design UI设计

页面以企业列表为主，顶部提供企业名称/统一社会信用代码、园中园、行业、纳管状态及更多筛选；右侧提供新增企业入口。列表默认展示企业名称、所属园中园、行业、主要产品、主要能源、企业标签、纳管状态、空间定位、最近更新和操作。新增/编辑采用分组表单，详情页展示基本身份、园区管理关系、空间信息、生产与用能基础特征、企业标签/资质和更新记录。

### 3.1.3. 能源与设施

#### 3.1.3.1. Introduce 介绍

能源与设施用于统一维护园区能源基础设施、能源节点及其长期流向关系，回答“能源从哪里来、经过什么节点、最终流向哪里”。页面包含“能源设施”和“能源流向”两个Tab，不按电力、天然气、热力、储能等能源类型拆成多个菜单。

企业仍保持为Enterprise主对象，能源网络层只通过enterpriseId或企业消费节点映射引用企业，不复制企业名称、行业、地址等主数据。能源与设施不承担月度能源消费量、结构趋势、TOP5或IOC线宽等结果维护。

#### 3.1.3.2. UI Design UI设计

能源设施Tab顶部提供节点名称、节点类型、能源类型、园中园、运行状态等筛选，主体列表展示节点名称、类型、能源类型、所属园中园、设计能力、运行状态、空间定位、最近更新和操作。能源流向Tab提供来源节点、去向节点、能源类型和状态筛选，列表展示来源→去向、能源类型/属性、生效时间、最近流量（只读）、数据来源、状态和操作。第一期列表为主，可提供地图视图用于定位和关系核验，但IOC承担态势地图展示。

1\. 进入“数据管理 \> 能源与设施 \> 能源设施”，系统读取EnergyNode。

3\. 节点角色分为SOURCE来源、FACILITY设施、CONSUMER用能；企业消费端可通过enterpriseId或消费节点映射关联Enterprise。

4\. 点击查看/编辑进入节点详情或编辑；停用节点前执行关系与历史数据引用校验。

#### 3.1.3.3.3. Output 输出

- 字段：节点名称、节点类型、能源类型、所属园中园、设计能力、运行状态、空间定位、最近更新、操作。

- EnergyNode仅保存稳定节点/设施属性，不保存月度能源流量。

- 企业主数据不得复制到能源节点表中；企业名称等显示信息从Enterprise读取。

- 本页不展示园区能源结构、月度趋势和企业TOP5。

3\. 绿电必须表达为energyType=电力、energyAttribute=绿色电力，并按需设置greenSourceType。

4\. 保存后节点可被能源流向关系引用；已有历史引用的节点停用后保留历史关系和数据。

#### 3.1.3.4.3. Output 输出

- 生成/更新EnergyNode主记录及其空间和扩展参数信息。

#### 3.1.3.4.4. Usage Limitation 约束与限制

- 不把绿色电力作为与电力并列的独立energyType。

- 类型扩展参数的具体数据库实现由研发决定，产品只要求前端按节点类型展示适用字段。

- 本期不建设完整设备资产台账，只维护对园区能源网络和IOC有价值的能源节点/设施。

#### 3.1.3.5. 能源流向关系查询与维护

| 能源类型      | 下拉框    | 否           | 电力/天然气/热力等             | —                          |

#### 3.1.3.5.2. Process 处理

1\. 系统读取EnergyFlowRelation并展示来源节点→去向对象的长期连接关系。

2\. 新增关系时用户选择来源、去向、能源类型、能源属性、绿电来源类型（适用时）及生效时间。

3\. 系统根据来源和目标节点支持的能源类型过滤可选能源，减少不合法组合。

4\. 列表中的“最近流量”仅从业务能源数据关联/聚合读取，不在本Tab单独编辑。

5\. 编辑关系时可调整属性和有效期；已有历史数据时不允许物理删除，只能停用或设置失效时间。

#### 3.1.3.5.3. Output 输出

- 字段：来源节点、去向节点/企业、能源类型、能源属性、所属园中园、生效时间、最近流量（只读）、数据来源、状态、操作。

#### 3.1.3.5.4. Usage Limitation 约束与限制

- EnergyFlowRelation表示长期关系，不与具体月份流量混为一张可编辑业务表。

- 企业存在唯一能源来源时，可直接将企业正式能源消费数据映射到有效流向关系；多来源供能场景本期不建设复杂通用分摊模型，可按项目实际补充来源分配。

- IOC流线宽度、能源结构和TOP5由正式事实数据聚合计算，不在关系表中维护。

#### 3.1.3.6. 流向关系校验、停用与历史保护

#### 3.1.3.6.1. Inputs 输入

| **输入项**     | **类型**  | **是否必填** | **范围**     | **备注**                                  |
|----------------|-----------|--------------|--------------|-------------------------------------------|
| 待保存流向关系 | 系统参数  | 是           | 当前关系表单 | —                                         |
| 停用操作       | 按钮/确认 | 条件         | 当前有效关系 | 已有历史流量/业务引用时使用停用而非删除。 |

#### 3.1.3.6.2. Process 处理

1\. 保存前校验source与target不能为同一对象。

2\. 校验能源类型与来源/目标节点支持能力一致。

3\. 校验同一有效期内不存在完全重复的来源→去向→能源类型/属性关系。

4\. 校验历史引用：已有期间事实或IOC历史追溯关系的记录不得物理删除。

5\. 停用后保留历史关系，新的业务期间不再自动匹配该关系。

#### 3.1.3.6.3. Output 输出

- 校验通过则保存；校验失败返回明确原因；停用后状态变更并保留历史。

#### 3.1.3.6.4. Usage Limitation 约束与限制

- 本期优先支持同类能源的“来源→设施→企业/用能节点”关系；天然气投入锅炉后转换为热力等跨能源转换不作为本页重点。

- 不根据节点名称自动推断缺失流向关系。

#### 3.1.3.7. 与业务数据及IOC联动

#### 3.1.3.7.1. Inputs 输入

| **输入项**              | **类型** | **是否必填** | **范围**                   | **备注**         |
|-------------------------|----------|--------------|----------------------------|------------------|
| EnergyNode/FlowRelation | 系统参数 | 是           | 当前有效节点和关系         | 提供网络骨架。   |
| 正式能源数据            | 系统参数 | 条件         | 当前期间BusinessDataRecord | 提供实际能源量。 |

#### 3.1.3.7.2. Process 处理

1\. IOC能源流向态势读取企业空间信息、EnergyNode和有效EnergyFlowRelation生成网络结构。

2\. 当前期间实际流量优先读取业务数据中的正式能源记录，并按有效关系关联到对应流线。

3\. 数据总览根据节点、关系和能源数据完整情况判断“能源设施/能源流向”数据域准备度。

4\. 从数据总览定位关系缺失时，跳转本页并携带园中园、企业/节点、能源类型等筛选条件。

#### 3.1.3.7.3. Output 输出

- 为IOC提供可追溯的节点、关系、能源类型/属性和当前期间事实来源。

#### 3.1.3.7.4. Usage Limitation 约束与限制

- IOC展示逻辑不反写能源设施或流向关系。

- 本期不建设独立月度EnergyFlowRecord人工维护入口。

### 3.1.4. 业务数据

#### 3.1.4.1. Introduce 介绍

业务数据是园区正式事实数据的统一查询、追溯与维护入口，回答“哪个企业或对象在什么期间发生了什么数据、值是多少、来源是什么、是否正式、是否存在质量问题、能否追溯”。页面包含能源数据、运营数据、碳排放数据、零碳专项数据四个Tab。

四类业务含义不同，但共享统一BusinessDataRecord基础框架和状态/来源规则。页面不展示园区经营态势、不判断1+5+5+1指标达标、不承担完整企业填报流程和完整专业碳服务流程。

#### 3.1.4.2. UI Design UI设计

页面顶部为四个Tab；统一筛选区包含企业/对象、园中园、期间、数据项、来源、数据状态/质量状态等，提供导出和必要的新增/录入入口。列表统一展示对象、期间、数据项、数值、单位、来源、数据状态、质量状态、最近更新和操作；各Tab在统一框架基础上增加领域专属字段。详情采用抽屉/弹窗展示来源、凭证、版本、计算/关联信息及问题入口。

#### 3.1.4.3. 统一查询、数据状态与来源

#### 3.1.4.3.1. Inputs 输入

| **输入项** | **类型**      | **是否必填** | **范围**                                                     | **备注**                 |
|------------|---------------|--------------|--------------------------------------------------------------|--------------------------|

#### 3.1.4.3.2. Process 处理

1\. 用户选择Tab和筛选条件执行查询，系统按BusinessDataRecord统一字段和当前数据域读取记录。

2\. dataStatus与qualityStatus独立展示；例如一条正式数据后续仍可被识别为异常。

3\. 系统根据sourceType显示来源名称，并在存在sourceRecordId时提供原始任务/接口/服务结果追溯入口。

4\. 列表支持查看详情、编辑草稿/待审核记录、正式数据修订、问题查看和必要的导出。

#### 3.1.4.3.3. Output 输出

- 统一列表字段：企业/对象、期间、数据项、数值、单位、来源、数据状态、质量状态、最近更新、操作。

#### 3.1.4.3.4. Usage Limitation 约束与限制

- 同一对象、数据项、期间及必要业务维度不得存在两条同时有效的正式数据；正式修改通过版本修订实现。

- qualityStatus用于摘要筛选，具体问题原因以关联DataIssue为准；不得出现问题已关闭但质量状态长期不一致的双重人工维护。

- 当前版本不要求四个Tab在数据库中物理使用同一张表，但产品逻辑、通用字段和追溯规则必须统一。

#### 3.1.4.6. 碳排放数据

#### 3.1.4.6.1. Inputs 输入

| **输入项**   | **类型**      | **是否必填** | **范围**                              | **备注**                             |
|--------------|---------------|--------------|---------------------------------------|--------------------------------------|
| 企业/对象    | 下拉/系统参数 | 是           | 企业/园区等核算对象                   | —                                    |
| 期间         | 月份/年份     | 是           | 当前及历史期间                        | —                                    |
| 排放范围     | 下拉框        | 是           | 范围一/范围二                         | 当前园区IOC一期核心边界。            |
| 排放来源     | 下拉/数据项   | 是           | 天然气、柴油、外购电力、外购热力等    | —                                    |
| 活动数据引用 | 系统参数/选择 | 是           | 已有能源/运营数据或必要的专项活动数据 | 优先引用已有正式事实，避免重复录入。 |
| 排放因子     | 系统参数/选择 | 是           | 因子值、单位、来源、版本、生效时间    | 需可追溯。                           |
| 排放量       | 系统计算/回流 | 是           | tCO₂e等                               | 保存结果及计算方法。                 |
| 数据来源     | 下拉/系统参数 | 是           | 专业服务回流/系统计算/园区确认等      | —                                    |

#### 3.1.4.6.2. Process 处理

1\. 系统读取或选择当前核算对象和期间适用的正式活动数据；能源消费已存在于能源数据时优先引用，不重复录入一份相同活动量。

2\. 系统关联适用排放因子及版本，生成或接收范围一/二排放结果。

3\. 排放结果保存计算方法、关联活动数据记录ID和因子来源/版本，以支持“排放结果→活动数据→排放因子”的追溯。

4\. 组织碳专业服务结果回流时，按统一sourceType/sourceRecordId记录来源。

#### 3.1.4.6.3. Output 输出

- 碳排放列表字段可包括企业/对象、期间、排放范围、排放来源、活动数据、因子、排放量、数据来源、状态。

#### 3.1.4.6.4. Usage Limitation 约束与限制

- 当前园区IOC一期以范围一+范围二为核心；范围三不因企业专业服务可能涉及而自动进入园区IOC。

- 碳排放总量不能只作为孤立结果保存，必须能追溯到活动数据和因子。

- 已有能源数据作为活动数据时不得复制形成第二份独立可编辑消费量。

- 排放因子完整版本库的专业能力可与碳核算模块统一建设，本页只要求当前排放结果可追溯所用因子。

#### 3.1.4.7. 零碳专项数据

#### 3.1.4.7.1. Inputs 输入

| **输入项**     | **类型**  | **是否必填** | **范围**                                                                                                                       | **备注**                   |
|----------------|-----------|--------------|--------------------------------------------------------------------------------------------------------------------------------|----------------------------|
| 对象类型       | 下拉框    | 是           | 企业/园中园/园区/公共建筑等                                                                                                    | 专项数据不强制只属于企业。 |
| 对象           | 下拉/搜索 | 是           | 当前对象类型下对象                                                                                                             | 保存objectType+objectId。  |
| 专项数据项     | 下拉框    | 是           | 可利用屋顶面积、光伏覆盖面积、星级绿建面积、超低能耗建筑面积、新能源交通工具数量、交通工具总数、碳足迹认证产品数量、能效诊断等 | 由DataItemDefinition驱动。 |
| 年度/期间      | 年份/日期 | 是           | 当前及历史                                                                                                                     | 专项数据以年度为主。       |
| 数值/状态/单位 | 动态输入  | 是           | 按数据项定义                                                                                                                   | 支持数值、布尔、文本等。   |
| 来源/凭证      | 来源+附件 | 条件         | 企业专项填报、园区维护、专业服务回流等                                                                                         | 验收数据应保留必要证明。   |

#### 3.1.4.7.2. Process 处理

1\. 用户选择专项对象、数据项和年度后录入基础组成事实。

2\. 比例类零碳指标必须分别保存可追溯的分子和分母基础数据，例如可利用屋顶面积和光伏覆盖面积，而不是只录入“覆盖率56%”。

3\. 系统按对象类型和DataRequirementRule判断当前专项数据是否适用，并在数据总览中反映完成/缺失状态。

4\. 正式专项数据供零碳指标管控统一计算和验收支撑。

#### 3.1.4.7.3. Output 输出

- 输出专项事实列表、来源/凭证和数据状态。

#### 3.1.4.7.4. Usage Limitation 约束与限制

- 零碳专项数据与运营数据按“日常持续经营事实”和“评价/验收专项事实”区分。

- 指标最终百分比、达标/未达标结论由零碳指标管控页面计算和展示，不作为基础事实在本页人工维护。

#### 3.1.4.8. 数据新增与批量导入

#### 3.1.4.8.1. Inputs 输入

| **输入项**                    | **类型**      | **是否必填** | **范围**         | **备注**                  |
|-------------------------------|---------------|--------------|------------------|---------------------------|
| 新增数据                      | 按钮          | —            | 当前Tab          | 园区必要场景直接新增。    |
| 导入文件                      | 文件上传      | 否           | 系统支持模板格式 | 用于历史初始化/存量迁移。 |
| 对象/数据项/期间/值/单位/来源 | 表单/文件字段 | 是           | 按当前数据域定义 | —                         |

#### 3.1.4.8.2. Process 处理

1\. 园区人员可在必要场景直接新增业务数据，系统要求明确数据域、数据项、对象、期间、值/单位、来源和必要凭证。

2\. 批量导入用于历史数据初始化、园区存量数据迁移等；系统执行对象ID/名称映射、数据项、单位、重复记录和基础校验。

3\. 存在错误时返回失败行和原因，不得将失败数据静默转为0或正式数据。

4\. 企业日常补数优先由填报任务触发，而不是要求企业直接使用园区业务数据录入入口。

#### 3.1.4.8.3. Output 输出

- 新增成功生成BusinessDataRecord；批量导入返回成功/失败数量和错误明细。

#### 3.1.4.8.4. Usage Limitation 约束与限制

- 正式数据生成前必须通过必要审核/确认规则；直接导入不能无条件绕过数据状态。

- 当前版本不建设独立通用数据采集菜单。

#### 3.1.4.9. 数据详情与来源追溯

#### 3.1.4.9.1. Inputs 输入

| **输入项** | **类型** | **是否必填** | **范围**         | **备注** |
|------------|----------|--------------|------------------|----------|
| recordId   | 系统参数 | 是           | 当前业务数据记录 | —        |

#### 3.1.4.9.2. Process 处理

1\. 点击“查看/追溯”后系统读取当前业务记录、对象、数据项、期间、值/单位、来源、凭证、状态、版本和关联问题。

2\. 企业填报来源展示taskId/submissionId；系统接口来源展示interface/external记录；专业服务回流展示serviceResultId；园区维护展示createdBy、操作记录和凭证。

3\. 碳排放结果额外展示活动数据和因子追溯；能源数据展示折标系数/版本。

4\. 存在DataIssue时提供“查看问题”入口，打开统一问题详情。

#### 3.1.4.9.3. Output 输出

- 输出完整数据详情、来源链路、版本信息和必要的业务关联。

#### 3.1.4.9.4. Usage Limitation 约束与限制

- sourceRecordId缺失时仍需保留sourceType和createdBy等最低追溯信息，并明确“无进一步来源记录”。

- 详情只展示真实来源，不补造接口、任务或凭证信息。

#### 3.1.4.10. 正式数据修订与版本控制

#### 3.1.4.10.1. Inputs 输入

| **输入项**           | **类型** | **是否必填** | **范围**           | **备注**               |
|----------------------|----------|--------------|--------------------|------------------------|
| recordId             | 系统参数 | 是           | 当前正式记录       | —                      |
| 修订值/单位/来源说明 | 表单     | 是/条件      | 当前数据项允许范围 | 需填写修订原因或来源。 |

#### 3.1.4.10.2. Process 处理

1\. 草稿/待审核记录可正常编辑。

2\. 正式数据点击“修订”后创建新版本，不直接覆盖旧版本；旧版本保留为历史。

3\. 同一逻辑数据（同对象、数据项、期间及必要业务维度）只保留一条当前有效正式版本。

4\. 修订后的数据重新触发质量校验、IOC/指标聚合及相关DataIssue判断。

5\. 已作废数据只读留痕，不参与当前计算。

#### 3.1.4.10.3. Output 输出

- 形成v1→v2等版本链；列表默认展示当前有效版本，详情可查看历史版本和修订原因。

#### 3.1.4.10.4. Usage Limitation 约束与限制

- 正式数据不得无痕覆盖。

- 历史IOC、指标或验收结果需要复核时，应能够追溯当时使用的数据版本；具体历史快照实现由研发设计。

#### 3.1.4.11. 与填报任务、数据事项和指标/IOC联动

#### 3.1.4.11.1. Inputs 输入

| **输入项**        | **类型** | **是否必填** | **范围**                 | **备注**               |
|-------------------|----------|--------------|--------------------------|------------------------|
| 缺失/异常数据事项 | 系统参数 | 条件         | DataIssue                | —                      |
| 填报任务结果      | 系统参数 | 条件         | taskId/submissionId      | 企业补数据完成后回流。 |
| 业务依赖          | 系统配置 | 条件         | IOC/零碳指标的数据项依赖 | 用于影响判断。         |

#### 3.1.4.11.2. Process 处理

1\. 数据总览或其他业务识别企业责任缺失后，可创建填报任务。

2\. 企业提交并经园区审核通过后，系统生成或更新BusinessDataRecord并设置为正式。

3\. 业务数据展示qualityStatus和“查看问题”入口，但不复制DataIssue完整处理流程。

4\. 指标模块读取业务数据的分子、分母和基础事实，负责公式、目标、结果和达标判断。

5\. IOC读取正式能源、碳排、专项事实及指标结果形成趋势、结构、TOP5、热力等展示。

6\. 正式数据更新后，系统刷新受影响的DataIssue、数据总览和业务应用结果。

#### 3.1.4.11.3. Output 输出

- 形成“发现问题→补数/修订→正式数据→业务应用→总览恢复”的闭环。

#### 3.1.4.11.4. Usage Limitation 约束与限制

- 填报任务负责企业补数据过程，业务数据负责审核通过后的正式结果；任务页面不得长期替代正式数据查询。

- 业务数据不维护零碳指标最终达标结论，也不为IOC单独建立趋势/排名/结构事实表。

# 4. Performance Requirements 性能需求

本版来源材料未给出统一的并发量、响应时间和数据规模SLA，因此本PRD不新增未经确认的硬性性能数字。研发评审时应结合企业数量、月度数据量、IOC聚合方式及部署环境补充性能基线。

- 列表类页面必须采用分页或等效的分段加载机制，避免一次加载全量历史数据。

- 数据总览聚合应使用后端聚合结果或缓存/预计算策略，前端不得逐企业逐数据项串行计算覆盖率。

- 同一页面各摘要、表格和下钻应使用同一查询条件和同一统计口径，避免局部异步刷新导致结果不一致。

- 批量导入应支持错误明细返回，避免单条错误导致用户无法定位问题。

- 具体响应时间、最大文件大小、并发用户数在研发技术设计阶段确认，并纳入测试基线。

# 5. Quality Attributes 质量需求

| **质量属性** | **要求**                                                                                    |
|--------------|---------------------------------------------------------------------------------------------|
| 一致性       | 企业、园中园、能源节点、数据项等跨模块引用使用稳定ID；名称变化不得造成历史关联断裂。        |
| 可追溯性     | 正式业务数据需记录来源类型、来源记录/创建人、版本和必要凭证；碳排结果可追溯活动数据和因子。 |
| 可审计性     | 正式数据修订保留历史版本；企业纳管、关键主数据和问题确认保留操作人及时间。                  |
| 数据完整性   | 无数据不按0处理；应报/适用规则与实际数据分离；问题状态可定位到对象、数据项和期间。          |
| 可解释性     | 数据总览不使用黑箱综合健康分；风险需能说明具体缺口及影响IOC/指标。                          |
| 权限边界     | 企业和管委会共享同一Enterprise，但治理字段、企业自维护字段和高风险标识权限清楚。            |
| 可扩展性     | 数据项使用统一编码和数据域；设施参数支持类型扩展；外部接口和复杂规则能力预留但不提前建设。  |
| 易用性       | 总览突出风险优先；跨页面下钻携带筛选上下文，避免用户跳转后重复定位。                        |

# 6. Other Requirements 其他需求

- 统一能源类型、能源属性、绿电来源、数据来源、对象类型、数据域、数据状态、质量状态等平台级字典口径。

- 数据总览、业务数据和填报任务中对“数据问题”的用户文案统一为“待处理数据事项/数据事项”，底层可使用DataIssue对象。

- 页面导出内容（如后续实现）必须与当前筛选条件、数据权限及当前有效版本一致。

- 原型Mock数据仅用于交互演示，不应被固化为正式业务规则或项目真实数值。

- 所有日期、年度和截至月份按园区业务时区统一处理；历史年度与当前年度的“截至月份”逻辑应区分。

# 7. External Interface 外部接口

当前数据管理模块以园区人工维护、企业填报、历史资料迁移及专业服务回流为主要实现边界。业务数据sourceType预留“系统自动获取”，能源设施的数据来源也预留外部系统同步，但本期不在左侧菜单单独建设数据采集/接口管理页面。

| **接口/来源类型**     | **当前要求**                                                               | **后续扩展**                                     |
|-----------------------|----------------------------------------------------------------------------|--------------------------------------------------|
| 企业填报任务          | 审核通过后生成/更新正式BusinessDataRecord，并保存taskId/submissionId追溯。 | 可扩展任务模板与自动催报规则。                   |
| 园区人工维护/批量导入 | 保存createdBy、导入批次及必要凭证。                                        | 可扩展标准模板、校验报告。                       |
| 专业服务回流          | 保存serviceResultId或等效来源标识。                                        | 可与组织碳、碳足迹、能效诊断等服务模块深度联动。 |
| 外部系统/API          | 本期仅保留sourceType和external/interface记录的兼容字段。                   | 后续接入电网、现有能碳平台、ERP/MES/IoT等。      |
